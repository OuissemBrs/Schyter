# DECISIONS

Why the engine behaves the way it does, and what was changed during the review
round. Each entry states the evidence that forced the decision.

---

## D1. The honest-run condition applies to the *claimant's* run only

**Decision.** A claim is evaluated only over traces in which the run that wrote
the claim has an honest agent *and* an honest peer. Other runs in the same trace
may involve the attacker.

**Evidence.** In `ns.spdl`, `claim_I1(I, Secret, ni)` is `VERIFIED` while
`claim_R1(R, Secret, ni)` is `FALSIFIED`, in the *same* protocol and the same
attack trace. If the condition covered every run in the trace, both would be
excluded, since the attack requires Alice to run with Mallory. If it covered no
run, both would fail.

**Consequence.** This is the mechanism NSL restores, and it is why
`docs/claims.md` has a whole section on the asymmetry. A user who wants "what if
Alice deliberately talks to Mallory?" must add a `Secret` claim on Alice's side or
use `--compromise`.

---

## D2. `attacker_new` is the Dolev-Yao closure difference, not the syntax

**Decision (bug fix).** The knowledge a trace step reports as learned is
`analyze(K_after) \ analyze(K_before)`, restricted to values and shared keys.

**Evidence.** `tools/independent_replay.py` failed on the NS trace:

```
FAIL out\golden\ns_R1.json: step 3: recorded attacker_new=[] but recomputation gives ['nr#1']
```

Step 3 is `{ni#2,nr#1}pk(I)` — a ciphertext for Alice. The old code used
`terms.leaves()`, which descends into ciphertext plaintext, so it reported the
sealed `nr#1` as learned. That is a lie in the renderer contract: the animation
would highlight terms Mallory never obtained.

**Impact.** Display only; no claim verdict changed. `Secret` claims use
`can_synthesize` over the real closure, never `attacker_new`. Re-running every
example produced identical verdicts, which is asserted by
`tests/unit/test_attacker_new.py::test_claim_verdicts_are_unaffected`.

---

## D3. `leaves()` keeps its old meaning; `attacker_new` stopped using it

**Decision.** `terms.leaves()` still returns *all* atomic sub-terms including
those sealed inside a ciphertext, because that is the useful notion for term
inspection (it is what `synthesizable ⟹ derivable` reasoning needs). Only the
knowledge panel switched to the closure difference.

**Why not change `leaves`.** Redefining it would silently change
`test_synthesizable_implies_derivable` and the general term utilities for no
benefit; the bug was never in `leaves`, it was in using it for a Dolev-Yao
question.

---

## D4. The independent replayer is a permanent test, not a one-off

**Decision.** `tests/integration/test_independent_replay.py` runs
`tools/independent_replay.py` over every falsifying trace of `ns`, `replay` and
`challenge_response_no_id`, and also asserts the tool *can* fail (by tampering
with a trace).

**Why.** A checker nobody runs catches nothing. The tamper test guards against
the checker silently becoming a no-op.

---

## D5. Reference values live in `expected_reference.json`, snapshots in `regression_snapshot.json`

**Decision.** Two files with two jobs:

* `examples/expected_reference.json` — hand-written from the specification and
  the literature, each entry carrying a `source` field. **This is the oracle.**
* `examples/regression_snapshot.json` — generated by `tools/make_snapshot.py`
  from the engine's own output. Used only to detect *changes*, never to decide
  whether an answer is right.

**Why.** The previous single `expected.json` was circular: regenerated from the
engine, so it could only ever confirm the engine. Splitting them means a wrong
engine answer now fails `test_reference.py` instead of silently rewriting itself.

**Consequence for this deliverable.** `test_reference.py` and
`test_regression.py` both run. Where they disagree, the disagreement is printed
as a table and analysed in DECISIONS.md rather than resolved by editing the
reference.

See D6–D10 for the individual disagreements found.

## D6. `cr` responder claims stay `VERIFIED`; the brief expected `FALSIFIED`

**Disagreement.** The review brief listed `cr: I1..I4 VERIFIED; R1..R4 FALSIFIED`,
and Issue 3 expected `cr R1..R4 are FALSIFIED, and the trace shows the attacker
sending nM`. The engine (and the hand-written reference) say all six claims of
`challenge_response.spdl` are `VERIFIED`.

**Why the reference says `VERIFIED`, with evidence.** In `cr.spdl` every message
is sealed under the *pairwise* key `k(A,B)`:

```
role A { fresh na; send_1(A,B, {A,na}k(A,B)); recv_2(B,A, {B,na}k(A,B)); }
role B { var na;   recv_1(A,B, {A,na}k(A,B)); send_2(B,A, {B,na}k(A,B)); }
```

`k(A,B)` is derived by `Attacker.analyze` only when one of the two agents is
compromised (`attacker._decompose`, the `shared-key` rule); with `M` alone
compromised it is never in the attacker's knowledge. So the attacker cannot build
*either* message, cannot answer *either* receive, and has no trace to offer. Bob's
claims therefore hold vacuously and non-vacuously: `B1 Alive(A)` because any Bob
run must have been fed by a real Alice run, and `B2 Nisynch(A)` because that
Alice run is mutually paired. The same argument covers `A1`–`A4`.

**Would attacker constants change this?** No, and this is the substantive point
of Issue 3 for this protocol. `nM`/`kM`/`dM` are *values*, not keys between two
honest agents. There is nothing the attacker can bind `na` to that makes
`k(A,B)` appear in its knowledge, so adding the constants opens no new state.
Confirmed empirically: after the change, all 38 claim verdicts across the six
examples are byte-identical (see `tests/unit/test_attacker_constants.py::
test_adding_attacker_constants_changed_no_verdict`), and a scan of every trace
the engine produces finds **zero** occurrences of `nM`, `kM` or `dM`.

**What would make the brief's expectation true.** A `cr` whose responder's first
receive were *not* under `k(A,B)` — for example `{A,na}pk(B)` with a bare-nonce
reply. In that design the responder's claims would indeed be falsifiable. That is
a different protocol from the one bundled here.

**Not a disagreement to resolve by editing the reference.** The reference and the
engine agree; both disagree with the brief, and the evidence is above. I am
asking for confirmation that `challenge_response.spdl` should keep its
pairwise-key design (see the questions in the final report).

## D7. `cr_noid` initiator `Alive`/`Niagree`/`Nisynch` are `VERIFIED`, not `FALSIFIED`

**Disagreement.** The brief listed `cr_noid: I1..I4 FALSIFIED; R1..R4 FALSIFIED`.
The reference and engine say `A1 FALSIFIED` and `A2`–`A4`, `B1`, `B2` `VERIFIED`.

**Why.** My first instinct agreed with the brief: in `challenge_response_no_id`
the reply is the bare nonce in the clear, so Mallory learns `na`, answers Alice
outright, and Alice completes with no Bob run — which falsifies `Alive`, and with
it `Niagree` and `Nisynch`. That argument is correct **in the unrestricted
model**, and it is exactly what the engine reports for `replay.spdl` (`A1`/`A2`
`FALSIFIED` for the same structural reason).

It does not apply here because of D1. The brief's own `recv_N(A,B,t)` convention
has `B` = self, and D1 restricts the **claimant's** peer to honest agents. Under
that restriction Alice always talks to Bob, Bob runs, and the agreement claims
hold. Only `A1 Secret(na)` breaks, because Mallory can read the cleartext reply on
the way past without *being* Alice's peer.

**Why D1 cannot be relaxed.** If the honest-peer condition did not apply to
agreement claims, then `ns.spdl`'s `I3`/`I4` would also be `FALSIFIED` (Alice
completes with peer `M` under Lowe's attack). The specification section 10
requires them `VERIFIED`. D1 is therefore forced by the specification, not chosen
for convenience.

**Consequence.** `cr_noid` shows exactly one thing — *secrecy fails without a
key, agreement still holds because of the honest-peer condition*. That is a
sharper lesson than "everything fails", and it is what the reference records.

## D8. `replay` claims are all `FALSIFIED`, not "R1..R4 VERIFIED; R5, R6 FALSIFIED"

**Disagreement.** The brief's skeleton had six claims for the replay example
(`R1`–`R6`, the last two falsified). `replay.spdl` has four (`A1`, `A2` = Niagree,
Nisynch on Alice; `B1`, `B2` = Niagree, Nisynch on Bob) and the reference says
all four are `FALSIFIED`.

**Why all four.** `replay.spdl` sends a single message `{A,na}` in the clear.

* On Bob's side (`B1`, `B2`): Mallory *builds* `{A,na}` from `Atom A` alone and
  injects it into Bob's `recv_1`. Bob's run completes with **no Alice run at
  all**, so no mutually paired partner exists. FALSIFIED, plainly.
* On Alice's side (`A1`, `A2`): Alice's run is honest (her peer is Bob, by D1),
  she sends and completes immediately. Nothing in the protocol obliges Bob to
  run, so the trace in which only Alice runs is a legal trace of this protocol.
  Her completion with no partner falsifies `Niagree`/`Nisynch`. FALSIFIED.

**Why this is the right reading.** `Niagree(P)` as defined in `docs/claims.md`
asserts "if I complete, P ran with me". A protocol in which the initiator never
waits for anybody cannot satisfy that, and reporting `VERIFIED` would be
claiming a property the protocol text does not have. The example exists to
demonstrate that; making half its claims pass would misrepresent it.

**On the label mismatch.** The brief's `R1`–`R6` numbering does not correspond to
any claim label in this repository, so I treated it as describing a different
example design rather than renaming labels to fit. I would rather have the brief
corrected than have me invent six claims for `replay.spdl`.

## D9. Attacker-generated constants are sound and were added, but are inert here

**Decision.** `nM: Nonce`, `kM: Key` and `dM: Data` are in the attacker's initial
knowledge (`attacker.ATTACKER_CONSTANTS`), and `Searcher._candidates` offers the
one matching a receive variable's declared type before the replayable atoms.

**What stayed forbidden.** Guessing an honest party's fresh value. The names
`nM`/`kM`/`dM` contain no `#`, while a run's fresh values are rendered
`name#run`, so they can never unify with `ni#1`. Three tests pin this:
`test_an_attacker_constant_never_unifies_with_a_run_fresh_atom`,
`test_the_attacker_cannot_produce_an_honest_nonce_before_it_is_sent` and
`test_no_fresh_atom_of_a_run_ever_enters_the_attacker_knowledge_directly`.

**Why the verdicts did not move.** D6 explains it for `cr`: the obstacle is a
key between two honest agents. Across all six examples the reachable receives an
honest run must satisfy are either sealed under a key the attacker lacks, or
already satisfiable with an atom it knew. A scan of every produced trace finds no
`nM`/`kM`/`dM` at all.

**What the change did buy.** Reachability is strictly larger on protocols that
take a bare nonce off the wire. `tests/unit/test_attacker_constants.py::
test_a_nonce_receive_can_be_answered_with_the_attacker_nonce` shows the attacker
delivering `nM` into a `Nonce` receive — a path that did not exist before — so
the capability is real even though the bundled examples do not exercise it.

## D10. Sharing one search between claims is sound, and is now checked

**Decision.** Keep the shared search, document it in
[`docs/architecture.md`](docs/architecture.md), and add `protoverify verify
--no-share` so the optimisation can be audited from the command line.

**Why it is sound.** The violation condition is not part of the search.
`Searcher._collect` evaluates every claim of the group against every terminal
trace, from the same state, the same substitution and the same partner role; only
the claim object differs. The one early exit in `_search_group` fires only when a
budget stopped the run (everything in the group is then `UNKNOWN`, which is the
right answer for all of them) or when *every* claim in the group already has a
counterexample. It never fires on a subset, so a claim that survives keeps the
search alive until the space is exhausted.

**Evidence.** `tests/integration/test_shared_search.py` compares, for all six
examples: the shared run against `share=False`; each claim alone against its entry
in the shared run (status *and* trace step list); and the state count being
constant across a group. All 14 tests pass, and `--no-share` produces identical
output from the command line:

```
$ protoverify verify examples/ns.spdl --no-share
R     R1     Secret   FALSIFIED  1995    0.95
R     R2     Secret   FALSIFIED  1995    0.97
```

Identical verdicts and identical state counts; only the wall clock differs.

## D11. The Manim path stays untested here, and says so precisely

**Decision.** Do not claim the Manim back-end works. Add
`tools/check_manim.sh` and `tools/check_manim.ps1` so the claim can be *checked*
by someone with the toolchain, and make the CLI name the missing piece.

**Evidence.** Running `tools/check_manim.ps1` on this machine:

```
1/3  python -c 'import manim'
  [FAIL] manim is not importable
2/3  ffmpeg -version
  [FAIL] ffmpeg is not on PATH
3/3  render SequenceScene at -ql
  [FAIL] manim produced no MP4 under out
RESULT: the Manim back-end could not be exercised here.
```

`pip install manim` fails here with `failed-wheel-build-for-install` (it builds
from source and needs ffmpeg plus Cairo/Pango headers). `manim_scenes.py` is
therefore compile-checked and `mypy --strict`-clean but never rendered; its test
is marked `@pytest.mark.manim` and skips.

**The fallback is what is tested.** `viz/export.py` now distinguishes the two
failures — `_manim_missing()` and `_ffmpeg_missing()` — because they have
different fixes, and each names the exact install command per platform. A `.mp4`
target is rewritten to `.gif` on the fallback path. The matplotlib path is
covered end to end: `run-example ns --animate --engine mpl` produces a GIF.

## D12. A shared key is symmetric, and symmetry lives in the unifier

**Bug.** `k(A,B)` and `k(B,A)` were two different terms that did not unify.

**Evidence.**

```
>>> solve(SymEnc(Tuple(Var('r1::na')), SharedKey(A, B)),
...       SymEnc(Tuple(Var('r2::nb')), SharedKey(B, A)))
None
```

These are the templates a *send* and its partner *recv* have in any protocol
written symmetrically — each role naming the shared key with its own parameter
first, which is how a human writes it. The search therefore could not match an
honest send with its partner's receive, silently losing traces. A lost trace can
turn a real attack into a `VERIFIED`.

**First attempt, and why it was wrong.** Canonicalising the two arguments in
`SharedKey.__post_init__` (sorting them) *looks* right and is subtly broken: the
sort order depends on whether an agent variable is bound yet. `k(a,B)` sorts to
`k(B,a)`; when `a` is later bound to `A` it becomes `k(B,A)`, which no longer
equals `k(A,B)`. Caught by
`test_a_shared_key_var_unifies_from_either_side`.

**Fix.** The terms keep the order they were written in, and
`unify._match_shared` matches both orderings, trying the swapped one on a *copy*
of the substitution so a failed first attempt cannot leave bindings behind. The
copy is committed only when the swapped match fully succeeds.

```python
if _match(a.left, b.left, s, required) and _match(a.right, b.right, s, required):
    return True
trial = dict(s)
trial_required = {n: set(t) for n, t in required.items()}
if _match(a.left, b.right, trial, trial_required) and _match(
    a.right, b.left, trial, trial_required
):
    s.clear(); s.update(trial)
    required.clear(); required.update(trial_required)
    return True
return False
```

**Impact.** No verdict on the bundled examples changes — none of them spell the
shared key in opposite orders. It is a latent bug that would bite the first
symmetric protocol written.

**Changed test.** `test_key_terms_unify_positionally` asserted that a shared key
unifies *positionally*, which is exactly the assumption being removed. It was
replaced by three tests that assert the real contract: symmetry, a variable on
either side, and the ciphertext regression case.

## D13. `analyze` must reach a fixed point, not a single sweep

**Bug (pre-existing, not introduced by any change in this review).**
`Attacker.analyze` popped each term off a worklist and applied `_decompose`
once. A rule that only becomes applicable after an earlier rule fires was
therefore never re-tried, so `analyze` did **not** saturate:

```
term = Tuple((Sign(Sk(A), Sk(A)), AsymEnc(A, Pk(A))))      # A compromised
analyze([term]) -> 4 terms, Atom(A) absent
analyze(once)   -> 5 terms, Atom(A) present                # strictly larger!
```

`can_synthesize` is documented as always being called on an `analyze`-closed
set. That contract was violated: the attacker's knowledge could grow on a second
call, so the attacker could be judged unable to build a term it can in fact
build — a false `VERIFIED`, not merely an incomplete one.

**Evidence it is pre-existing.** The identical probe run against commit `bb4bafd`
(the only commit, before any of this work) prints the same `IDEMPOTENT: False`.
The property test `test_analyze_is_idempotent` had started failing in this
working tree only because hypothesis had cached the counterexample; the
fresh-database run in the original worktree simply had not found it yet. The
direct probe, not the test outcome, is the evidence.

**Fix.** Iterate to a fixed point: repeat a full sweep over the closure until a
sweep derives nothing new.

```python
changed = True
while changed:
    changed = False
    for term in list(closure):
        for derived, rule, source in self._decompose(term, closure):
            if derived not in closure:
                closure.add(derived); newly.append(derived)
                derivations.append(Derivation(derived, rule, source))
                changed = True
```

**Impact.** No verdict on the bundled examples changes: the counterexample needs
a compromised agent's `sk` to be *derived from* a signature, which no bundled
protocol does. But the `can_synthesize`-on-a-closed-set contract now actually
holds.

**Note.** This is a good argument for keeping `tests/property/` and for distrusting
a green run backed by a cold hypothesis database.
